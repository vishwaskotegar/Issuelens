# ADR-002: LangChain Provider Adapter with Structured Output and Snapshot Provenance Binding

- **Status**: Accepted
- **Date**: 2026-10-29
- **Deciders**: Senior Engineer / IssueLens Maintainers
- **Phase**: Phase 3: First End-to-End Report
- **Nature of Rationale**: Original

---

## 1. Context and Problem Statement
IssueLens transforms public GitHub bug reports into evidence-backed investigation reports. Generating an investigation report requires orchestrating an LLM to analyze issue context and retrieved code evidence, extracting ranked hypotheses, observed facts, suggested tests, and limitations while defending against prompt injection and hallucinated citations.

Key architectural requirements:
1. **LangChain & LangGraph Compatibility**: The build specification product thesis mandates LangGraph for agent orchestration in Phase 5 and LangChain integrations where useful. Adopting LangChain's `BaseChatModel` abstraction and structured output capabilities in Phase 3 establishes a direct foundation for the upcoming Phase 5 state machine nodes.
2. **Deterministic Hermetic Testing**: Automated test suites must run completely offline without requiring network access, live API credentials, or paid accounts.
3. **Structured Output Invariants**: Reports must strictly conform to a typed Pydantic schema ([`InvestigationReport`](file:///c:/Projects/Issuelens/src/issuelens/agent/report.py#L87-L147)) containing observed facts, ranked hypotheses citing evidence IDs, verification steps, suggested tests, and limitations.
4. **Authoritative Provenance Separation**: Provenance coordinates (the pinned commit SHA, canonical issue URL, repository identity, and exact line-numbered evidence snippets) must be authoritatively bound by the system, rather than asked to be memorized or reproduced by the LLM.
5. **Safety Boundaries & Prompt Injection Defense**: Issue bodies, user comments, and investigated source code are untrusted external text. The system must defend against prompt injection attempts seeking to divert agent behavior or trick the assistant into falsely claiming tests passed.

---

## 2. Decision Made
We implemented a LangChain-powered structured output architecture in `src/issuelens/agent/` composed of:
1. **`InvestigationReportPayload` & `InvestigationReport` Separation**:
   - [`InvestigationReportPayload`](file:///c:/Projects/Issuelens/src/issuelens/agent/report.py#L51-L84): Contains solely the analytical output generated by the LLM (`summary`, `observed_facts`, `hypotheses`, `missing_information`, `suggested_tests`, `recommended_next_steps`, `limitations`).
   - [`InvestigationReport.from_payload(...)`](file:///c:/Projects/Issuelens/src/issuelens/agent/report.py#L149-L177): Authoritatively binds the LLM's analytical payload with the verified snapshot provenance (`run_id`, `issue_url`, `repository`, pinned `commit_sha`, verified `evidence` items, and enforced `verification_status="not_run"`).
2. **`LLMClientProtocol`**: An explicit asynchronous typing protocol defining `generate_report_payload(messages: list[BaseMessage]) -> InvestigationReportPayload`.
3. **LangChain Adapters**:
   - [`LangChainLLMClient`](file:///c:/Projects/Issuelens/src/issuelens/agent/llm.py#L35-L95): Wraps any LangChain `BaseChatModel` and binds it with `chat_model.with_structured_output(InvestigationReportPayload)`. Translates vendor-specific rate limits, timeouts, and auth failures into typed IssueLens domain exceptions.
   - `create_langchain_chat_model()`: Factory instantiating `ChatOpenAI` (for OpenAI, Ollama, Groq, OpenRouter) or `ChatAnthropic` (for Anthropic Claude).
   - [`MockLLMClient`](file:///c:/Projects/Issuelens/src/issuelens/agent/llm.py#L98-L162): Completely offline, deterministic client for test suites and local simulations without network calls or API keys.
4. **Prompt Injection Isolation**:
   - `build_investigation_messages()` builds LangChain `SystemMessage` and `HumanMessage`.
   - Untrusted issue metadata and code evidence are strictly wrapped in XML boundary tags: `<untrusted_issue_data>` and `<untrusted_repository_evidence>`.
   - `verification_status` is explicitly constrained to `"not_run"`.
5. **Orchestrator Service**:
   - [`InvestigationService`](file:///c:/Projects/Issuelens/src/issuelens/agent/service.py#L53-L170) orchestrates context ingestion, repository snapshot acquisition, lexical search, evidence building, message construction, LangChain structured completion, and report validation.

## 3. Alternatives Considered

### Alternative A: Custom Low-Level HTTP REST Adapters (`httpx` directly)
- **Description**: Writing custom HTTP serialization and header logic for OpenAI and Anthropic REST endpoints.
- **Pros**: Zero third-party LLM dependencies beyond `httpx`.
- **Cons**: Requires manually maintaining OpenAI and Anthropic tool/function calling schemas, response format parsers, and custom markdown stripping. Does not provide native compatibility with LangGraph state nodes planned for Phase 5.

### Alternative B: Direct Pydantic Output Parsers Without Tool Calling
- **Description**: Asking the LLM to write raw JSON into standard message text and parsing it with `PydanticOutputParser`.
- **Pros**: Works with older models lacking tool/function calling support.
- **Cons**: Significantly higher parse failure and JSON truncation rate. Modern models natively support tool-calling and structured outputs (`with_structured_output`) with near-zero syntax errors.

---

## 4. Reasons for Choosing the Selected Approach

1. **Direct Alignment with Product Specification**: The specification thesis establishes LangGraph and LangChain integrations as standard for the agent layer. Standardizing on `BaseChatModel` in Phase 3 ensures a frictionless upgrade to Phase 5.
2. **Schema-Enforced Tool Calling**: LangChain's `.with_structured_output(InvestigationReportPayload)` leverages native provider function calling / response format guarantees, virtually eliminating JSON formatting errors.
3. **Decoupled Architecture**: `LLMClientProtocol` hides the underlying model vendor from `InvestigationService`. Tests easily inject `MockLLMClient` or `FakeStructuredChatModel`.
4. **Provenance Integrity**: Separating the analytical payload (`InvestigationReportPayload`) from the full report (`InvestigationReport`) ensures the LLM cannot hallucinate or mutate the pinned commit SHA, issue coordinates, or code citations.
5. **Prompt Injection Defense**: Boundary enclaves and system directives ensure external text is treated strictly as passive data.

---

## 5. Benefits, Drawbacks, and Trade-offs

### Benefits
- Provider flexibility: Seamlessly switch between OpenAI, Anthropic, or self-hosted models via standard LangChain chat models.
- Guaranteed schema conformance: Provider-level structured output minimizes malformed JSON retries.
- Fast offline testing: Complete test suite runs in under 5 seconds with zero external network dependencies.

### Drawbacks & Limitations
- Transitive dependencies: Introduces `langchain-core`, `langchain-openai`, and `langchain-anthropic`.
- Single-turn execution: Phase 3 executes a single structured pass; multi-turn follow-up loops are reserved for Phase 5.

---

## 6. Consequences for Future Development
- **For Phase 4 (Evidence Validation)**: Validation logic will inspect the returned `InvestigationReport`, verifying that all `supporting_evidence_ids` in each hypothesis resolve to valid code hits in the pinned repository snapshot.
- **For Phase 5 (LangGraph)**: The `BaseChatModel` instances and `LLMClientProtocol` integrate directly as state graph node invokers.
